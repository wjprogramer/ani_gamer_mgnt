動畫瘋個人管理工具：可行性評估

狀態：規劃中（尚未動工）・建立日期：2026-10-23

結論：四項需求在技術上都可行。最大的不確定性在於「準確偵測真正開始播放（排除廣告）」和「首頁卡片只帶集數 sn、沒有動畫 sn」這兩點，實作前要先拿實際 DOM 驗證。 架構建議第一階段只做 Chrome Extension（local-first），等真的需要跨瀏覽器或多來源時再加本機 server。

1. 需求摘要

  1. 隱藏動畫：在首頁、所有動畫列表等頁面的動畫卡片上加上「隱藏」按鈕。
  2. 評論：針對動畫撰寫評論，儲存在本機。
  3. 本機資料庫：記錄自有 ID、動畫瘋 ID、動畫名稱、封面（存到本機）；偵測到播放時自動記錄觀看日期時間（因為動畫瘋的觀看紀錄過一段時間會被刪除）。
  4. 技術架構：評估 web server（React + Express／Next.js）+ Chrome Extension 是否合適。

2. 可行性總覽

需求可行性主要風險
隱藏動畫高各頁卡片 DOM 結構不同；部分卡片只有「集數 sn」，要再對應回動畫 sn
評論高純本機 CRUD，幾乎沒有風險
動畫資料與封面高封面圖片網址可能改版；可能有防盜連（由 extension 背景下載可以避開）
自動記錄觀看中高要排除片頭廣告、年齡確認、重新整理或續看造成的重複紀錄
網站改版的耐受度中所有 DOM 選擇器都可能失效，要集中管理並做好失效時的提示

3. 各需求分析

3.1 隱藏動畫

做法：用 content script 注入 ani.gamer.com.tw，以 MutationObserver 偵測動畫卡片（包含延遲載入的部分），在卡片上插入按鈕，並依本機的隱藏清單把卡片隱藏起來。

  • 識別方式：動畫瘋有兩種 sn。animeRef.php?sn= 是動畫（作品），animeVideo.php?sn= 是單集。隱藏應該以「動畫」為單位，但首頁「新上架」這類卡片通常連到單集，所以需要一份 集數 sn → 動畫 sn 的對應快取。查不到時，在背景抓一次單集頁面來解析，結果存進快取。
  • 涵蓋頁面：除了首頁和所有動畫列表，還要考慮搜尋結果、排行榜、季番表、播放頁的推薦區。建議做一份「頁面 → 卡片選擇器」設定表，逐頁擴充。
  • 隱藏方式：可以選完全移除、半透明淡化，或摺疊成一行「已隱藏：XXX（還原）」。建議預設用摺疊，避免誤按後找不回來。
  • 要有一個「暫時顯示全部」的開關，以及隱藏清單的管理頁。
  • 每季會有續作（第二季通常是另一個動畫 sn），要考慮是否「連同續作一起隱藏」。

3.2 評論

  • 在動畫頁（animeRef）和播放頁上注入評論面板，或做成 extension 的 side panel。
  • 建議欄位：評分、內文、是否含劇透、建立與更新時間。可以考慮支援單集評論（掛在集數上）。
  • 評論是自己寫的、無法重新取得的資料，備份機制的優先度最高（見第 6 節）。

3.3 動畫資料、封面與觀看紀錄

  • 中繼資料：第一次遇到某部動畫時（瀏覽動畫頁或播放頁），解析頁面上的名稱、封面網址和動畫 sn 後建檔。
  • 封面：由 extension background（service worker）用 fetch 下載。只要有 host_permissions 就不受頁面 CORS 限制，下載後以 Blob 存進 IndexedDB，或交給本機 server 存成實體檔案。
  • 播放偵測：
    • 監聽播放頁 <video> 的 playing 和 timeupdate 事件。
    • 動畫瘋在正片前會播廣告，可能用同一個播放器。判斷規則建議：廣告層不存在，且正片的 currentTime 連續前進超過 N 秒（例如 30 秒）才算開始觀看。
    • 除了開始時間，也記錄最後進度與片長，可以推算是否看完（例如超過 85%）。
    • 去重：同一集在 X 小時內再次播放，就合併成同一筆觀看紀錄（只更新進度），避免重新整理或續看時產生多筆。
    • 有可能同時開多個分頁，所以紀錄要以分頁為單位寫入，並能容忍並發。
建議優先處理：動畫瘋現有的觀看紀錄頁會隨時間被刪除。工具做好後，第一件事應該是做一個一次性匯入，把觀看紀錄頁上現有的內容爬進本機，否則這段期間的資料會流失。

4. 技術架構評估

方案優點缺點
A. 只有 Extension
（React 管理頁 + IndexedDB）		 不必另外啟動 server，打開瀏覽器就能用；觀看紀錄不會因為 server 沒開而遺漏；開發與部署最簡單 資料綁在某個瀏覽器 profile；移除 extension 時 IndexedDB 會一起刪除；其他瀏覽器無法共用
B. Extension + 本機 Server
（你目前的構想）		 資料存在硬碟（SQLite + 封面檔案），好備份、好查詢；之後要加其他來源、其他瀏覽器都容易 每次看動畫都得先開 server，沒開時事件會遺失，所以要在 extension 端做佇列重送；要多維護一個服務
C. Local-first 混合（建議） Extension 自己就能完整運作；資料層抽象化，之後可以把資料同步到本機 server 或匯出成檔案 需要設計同步邏輯（不過第一階段可以只做匯出／匯入）
D. Userscript（Tampermonkey） 上手最快 儲存空間和 UI 能力有限，不適合長期擴充，不建議

建議

  • Extension 框架：用 WXT（或 Plasmo）+ React + TypeScript。可以處理 MV3、HMR 和打包，比手刻 manifest 省力很多。
  • 儲存：用 IndexedDB（搭配 Dexie.js），並宣告 unlimitedStorage 權限。
  • 管理介面：直接做成 extension 的 options page 或 side panel（React），不需要另外的 web server。
  • 如果之後加 server：這是單人使用的本機工具，不需要 Next.js，SSR 和 SEO 在這裡都派不上用場。用 Hono／Express + SQLite，前端用 Vite + React 會更輕量。
  • 呼叫 localhost 的限制：Content script 的請求受頁面 CORS 和 Private Network Access 限制，呼叫 localhost 一律要透過 background service worker 轉送。
  • MV3 的 service worker 隨時會被關閉，狀態不能只放在記憶體裡。

5. 資料模型草案

核心原則：自有 ID 與來源 ID 分開。一部動畫可以對應多個來源（動畫瘋、未來的其他網站）。

anime            id (ULID), title, alt_titles[], cover_blob_id, hidden, hidden_at,
                 hidden_reason, created_at, updated_at
anime_source     anime_id, source ('bahamut'), external_id (animeRef sn),
                 url, raw_meta (JSON), first_seen_at
episode          id, anime_id, source, external_id (animeVideo sn), label ('第 3 集'),
                 sort_order
watch_event      id, episode_id, anime_id, started_at, last_seen_at,
                 progress_sec, duration_sec, completed, source ('auto' | 'import')
review           id, anime_id, episode_id?, rating?, content, spoiler,
                 created_at, updated_at
cover            id, anime_id, blob / file_path, source_url, fetched_at
sn_cache         source, episode_sn → anime_sn  （隱藏功能用）
  • ID 建議用 ULID 或 UUIDv7（可依時間排序，未來多裝置合併也不會衝突）。
  • 名稱建議也存日文原名或英文名（alt_titles），方便未來和其他網站比對同一部動畫；必要時可以再對應 AniList 或 MyAnimeList 的 ID。

6. 你可能沒考慮到的事

  1. 資料備份與遺失：移除 extension、清除瀏覽器資料、換電腦都可能讓資料消失。需要 JSON 匯出／匯入（含封面的 zip），最好再加上定期自動匯出。
  2. 歷史觀看紀錄的匯入：見 3.3。現在就有資料正在流失。
  3. 其他裝置：在手機 App 或電視上看的紀錄抓不到。可以接受嗎？還是要提供手動補登？
  4. 集數 sn 和動畫 sn 的對應：隱藏和觀看紀錄都需要，是基礎設施，不是附帶功能。
  5. 廣告與年齡確認：會讓「按下播放」不等於「開始看正片」。
  6. 網站改版：選擇器要集中在一個檔案裡；抓不到元素時在 extension 圖示上顯示警示，不要默默失效。可以存幾份實際頁面的 HTML 當成測試資料。
  7. 隱藏的粒度：要隱藏續作或同系列嗎？要不要支援依類型或關鍵字自動隱藏？
  8. 已看過的狀態：既然有觀看紀錄，可以順便在卡片上標示「看到第 N 集」或「看完」，價值不輸隱藏功能。
  9. 請求頻率：背景抓單集頁和封面時要節流並快取，避免對動畫瘋造成負擔或被擋。
  10. 著作權與使用條款：封面只供個人本機使用、不對外散佈；只修改自己瀏覽器的畫面，風險很低。但工具不要做成公開分享資料的服務。
  11. 時區：時間一律以 UTC 儲存（ISO 8601），顯示時再轉成本地時間。
  12. Schema 版本與遷移：IndexedDB 和 SQLite 都需要從一開始就規劃版本遷移。

7. 待你決定

  • 第一階段是否接受「只有 Extension、資料存在瀏覽器」，再搭配匯出備份？還是一開始就要求資料以實體檔案的形式存在硬碟上？
  • 隱藏後的呈現方式：完全移除、淡化，還是摺疊？
  • 評論要不要支援單集？要不要有評分？
  • 「觀看」的判定門檻：看了幾秒才算？看完的比例要設多少？
  • 會不會在多台電腦或多個瀏覽器上使用？（這會決定是否需要 server 或同步）

8. 建議里程碑

  1. M0 調查：實際擷取首頁、所有動畫、動畫頁、播放頁、觀看紀錄頁的 DOM，確認選擇器、sn 的取得方式和廣告的行為。
  2. M1 基礎：WXT 專案、資料層（Dexie）、動畫自動建檔、下載封面、匯出／匯入。
  3. M2 觀看紀錄：播放偵測、去重，以及匯入動畫瘋現有的觀看紀錄。
  4. M3 隱藏：卡片按鈕、sn 對應快取、隱藏清單管理。
  5. M4 評論：評論面板與管理頁。
  6. M5（選做）：本機 server 同步、多來源支援。
